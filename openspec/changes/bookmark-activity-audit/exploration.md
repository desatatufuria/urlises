# Exploration: bookmark/folder activity auditing (actor-attributed create/update/delete)

## Current State

**`activity` package** (`backend/internal/activity/service.go`) — `Service.Record(ctx, tx, orgID, actorUserID, kind, targetType, targetID, metadata) error` writes one `activity_events` row inside the caller's own transaction, before commit. `organization_id` is `NOT NULL` (`backend/migrations/000012_activity_events.sql:3`). The package's own doc comment (`service.go:6-7`) claims "zero callers in this work unit" — that comment is **stale**: `activity.Record` is already wired into `organizations/service.go` (9 call sites), `workspaces/service.go` (6 call sites), and `groups/service.go` (5 call sites), confirmed via `grep` and `main.go` wiring. Every existing caller resolves an `organizationID` before calling `Record`; `workspaces/service.go` already has the exact resolver a bookmark/folder integration would need to reuse: `loadWorkspaceOrganizationID(ctx, tx, workspaceID)` (used at `workspaces/service.go:327`).

**`bookmarks` package** (`backend/internal/bookmarks/service.go`, read in full) — `Service{pool, access}` has no `organizationID` concept and no `activity.Service` dependency today. Every public mutator (`CreateFolder`, `UpdateFolder`, `DeleteFolder`, `CreateBookmark`, `UpdateBookmark`, `DeleteBookmark`) is a thin wrapper: `pool.Begin` → call a `*Tx`-suffixed sibling with the same name → `tx.Commit`. The `*Tx` variants already accept `pgx.Tx` and are the actual mutation logic, plus `ApplyPreparedFolderPatchTx`/`ApplyPreparedBookmarkPatchTx` for the prepared-patch path. **Every mutation already runs inside a transaction that is available at the exact point an `activity.Record` call would need to go** — this part is structurally cheap, not invasive.

**`bookmarks.RegisterRoutes`** (`backend/internal/bookmarks/handler.go`) exists — registers `POST /workspaces/{workspaceId}/folders`, `PATCH /folders/{folderId}`, `DELETE /folders/{folderId}`, `POST /workspaces/{workspaceId}/bookmarks`, `PATCH /bookmarks/{bookmarkId}`, `DELETE /bookmarks/{bookmarkId}` directly against `bookmarks.Service`. **It is dead code**: grep across the whole backend, including `cmd/api/main.go`, finds zero callers of `bookmarks.RegisterRoutes` anywhere. `cmd/api/main.go:162` instead wires `syncapi.RegisterBookmarkRoutes` — the **identical** HTTP method+path set, but backed by `sync.Service`/`sync.PostgresStore`, not `bookmarks.Service` directly. Both handler sets can't even be mounted on the same mux simultaneously (path collision). **Conclusion: every live, reachable bookmark/folder mutation in the running server goes through `sync.PostgresStore`, with no distinct "admin-console-triggered" code path existing today.**

**`sync` package** (`backend/internal/sync/postgres.go`, `service.go`, `bookmark_routes.go`, `types.go`, read in full) — Each of `PostgresStore.CreateFolder`/`UpdateFolder`/`DeleteFolder`/`CreateBookmark`/`UpdateBookmark`/`DeleteBookmark` is its own HTTP route AND opens its own `pool.Begin()`/commits independently via `runMutation`/`runDeleteMutation` (`postgres.go:264-342`). **There is no bulk/batch sync endpoint and no single "sync round-trip" transaction** — every individual bookmark/folder mutation is already one HTTP request and one DB transaction, exactly like the `activity`-wired org/workspace/group mutations. `recordEvent` (`postgres.go:344-392`) already writes one `sync_events` row per mutation (not summarized), so there's an existing precedent for one-row-per-mutation event tables in this exact code path — just a separate table (`sync_events`), presumably retained/pruned differently than `activity_events` (not confirmed — retention policy wasn't investigated here).

**Actor availability** — every sync mutation route requires `auth.PrincipalFromContext(r.Context())` and threads `principal.UserID` straight through: `bookmark_routes.go` → `service.CreateFolder(ctx, principal.UserID, ...)` → `PostgresStore.CreateFolder(ctx, userID, ...)` → `s.recordEvent(ctx, tx, userID, ...)`, which is already persisted as `sync_events.user_id`. **A concrete actor user ID is already present at every single bookmark/folder mutation call site today — no new actor-plumbing is needed** to attribute "who did it."

**Extension side** (`extension/src/background/projection.ts`, `bookmark-listeners.ts`, partial read) — this is the finding that most changes the volume story. `doResyncWorkspace` (bootstrap/full resync, i.e. "initial sync") calls `materializeFolder`/`materializeBookmark`, which write directly into the **local Chrome bookmark tree** via `chrome.bookmarks` APIs, sourced from `getWorkspaceTree` (a GET) + `replayEvents`. **This path never calls a backend mutation endpoint** — a first-time/full workspace resync generates **zero** backend writes and thus zero `activity_events` rows under any design considered here. The actual backend-mutation-generating path is the opposite direction: `chrome.bookmarks.onCreated/onChanged/onMoved/onRemoved` (`bookmark-listeners.ts`) → `handleBookmarkCreated`/`handleBookmarkChanged`/`handleBookmarkRemoved` (`projection.ts`) → `apiCreateBookmark`/`apiCreateFolder`/`apiUpdateBookmark`/`apiUpdateFolder`/`apiDeleteBookmark`/`apiDeleteFolder`, one backend HTTP call (and one backend transaction) per Chrome event. **The realistic volume risk is a burst of individual `onCreated` events fired by Chrome's own native bulk-import ("Import bookmarks from HTML/other browser") or a large drag-and-drop, not a "batch sync payload"** — no batch payload structure exists to design around. No test fixture or integration test seeds a large mutation batch — no in-repo evidence of a "typical/max batch size" to cite; the volume concern is architectural (Chrome can fire hundreds of `onCreated` events in seconds during a native import), not something the current test suite has ever modeled.

**`admin-web` Activity page** (`admin-web/src/features/activity/ActivityPage.tsx`, `queries.ts`; `backend/internal/activity/handler.go`) — `GET /organizations/{organizationId}/activity` takes only `limit` (clamped 1-100, default 50) and `cursor`; **there is no `kind` filter anywhere** — not in the SQL (`ListByOrganization`'s query is `WHERE e.organization_id = $1` plus cursor predicate only), not in the HTTP handler, not in `listOrgActivity`/`useOrgActivity`, not in the UI. `ActivityPage.tsx` is a flat, unfiltered, newest-first "Load more" table. The composite index `idx_activity_events_org_created_id (organization_id, created_at DESC, id DESC)` means raw pagination *query performance* would hold up fine even at 100x volume (it's an indexed range scan bounded by `LIMIT`, not a full scan) — this is **not a database-performance risk**. It is a **product/UX risk**: an admin looking for a low-frequency event ("who revoked workspace access last Tuesday") would have to click "Load more" through however many bookmark-noise rows were interleaved, with zero way to filter them out.

## Affected Areas

- `backend/internal/bookmarks/service.go` — every `*Tx` mutator needs an `activity.Record` call; `Service` needs an `activity.Service` dependency and a workspace→organization resolver.
- `backend/internal/workspaces/service.go` — `loadWorkspaceOrganizationID(ctx, tx, workspaceID)` (existing, `service.go:327`) is the pattern to reuse/extract for bookmarks' org lookup.
- `backend/internal/sync/postgres.go` — `recordEvent` and the six `PostgresStore` mutation methods are the actual live call sites (since `bookmarks.RegisterRoutes` is dead code); if `bookmarks.Service` records activity internally, `sync.PostgresStore` gets it for free since it calls `bookmarks.Service`'s `*Tx` methods. If instead activity is recorded at the `sync` layer, it needs its own wiring since `sync` doesn't currently reuse `bookmarks.Service`'s own top-level (non-Tx) methods.
- `backend/internal/activity/service.go` — new `Kind` constants (e.g. `bookmark.created/updated/deleted`, `folder.created/updated/deleted`) would follow the existing `{resource}.{action}` naming already used both by `activity.Kind` and, independently, by `sync`'s `event_type` string literals — naming is already consistent, but the two are structurally separate enums/tables.
- `backend/internal/bookmarks/handler.go` — dead code; any design that assumes a live "manual console edit" path distinct from sync must first decide whether to revive/wire this (out of scope for "just add auditing") or accept there is no such live distinction today.
- `admin-web/src/features/activity/ActivityPage.tsx`, `queries.ts`, and `backend/internal/activity/handler.go`/`service.go` — would need a `kind`/category filter (backend query + HTTP param + UI control) if bookmark/folder events are mixed into the same feed at meaningfully higher volume, to keep the admin-relevant low-frequency events findable.
- `extension/src/background/projection.ts`, `bookmark-listeners.ts` — not something this change needs to touch (actor + tx already flow correctly end-to-end from here down to the backend), but they are the actual source of the volume risk (native Chrome bulk-import event bursts), not a designed batch payload.

## Approaches

1. **Audit every single bookmark/folder mutation as its own `activity_events` row** — reuse the exact `organizations`/`workspaces`/`groups` pattern: add `activity.Record` inside `bookmarks.Service`'s existing `*Tx` methods (or at `sync.PostgresStore`'s call sites), resolving `organizationID` via a `loadWorkspaceOrganizationID`-style helper.
   - Pros: Structurally trivial given that a `pgx.Tx` and a real actor `userID` are *already* present at every mutation site — this is the smallest, most consistent-with-existing-code option. No new "batch" abstraction to design since none exists in the sync protocol.
   - Cons: Confirmed real volume risk comes from Chrome-native bulk imports firing bursts of individual `onCreated` events, each becoming its own backend transaction and its own `activity_events` row — potentially hundreds to thousands of rows in seconds. Floods the unfiltered `ActivityPage.tsx` feed (no `kind` filter exists) with low-value noise, burying the low-frequency admin-relevant events it was designed around.
   - Effort: Low (backend wiring) + Medium if the `ActivityPage` filter gap is also addressed in the same change.

2. **Audit only via a distinct "manual console" path, exclude extension sync mutations.**
   - Grounded finding: **this distinction does not exist in live code today.** `bookmarks.RegisterRoutes` (the only code that would represent "a one-off admin-web-triggered edit") is dead/unwired; every reachable bookmark/folder mutation, regardless of actor, currently flows through `sync.PostgresStore`. There is no live signal to reliably distinguish "console" from "extension sync" today.
   - Pros: Would cleanly avoid the volume problem, if it existed.
   - Cons: Not implementable without first building a new capability (reviving `bookmarks.RegisterRoutes` behind a real admin-web bookmark editor, or inventing an origin-based classification) — this is out of scope for "add auditing to what exists" and doesn't match how the system is actually used today.
   - Effort: High (requires building a feature that doesn't exist, not just auditing one).

3. **A batched/summarized activity event per sync round-trip** (e.g., one `sync.batch_applied` event with a count).
   - Grounded finding: **there is no sync round-trip/batch unit to summarize.** Every mutation is already its own independent HTTP request and its own independent DB transaction; there's no wrapping transaction or batch envelope to hang a single summarized event off of. Implementing this would require inventing a new aggregation layer (e.g., a time-windowed counter keyed by workspace+actor, flushed periodically) that doesn't correspond to any existing request/transaction boundary in the code.
   - Pros: Would control volume well if built.
   - Cons: Highest design complexity of the options surveyed; a genuinely new mechanism, not a wiring task.
   - Effort: High.

4. **A separate, differently-retained audit mechanism for bookmark/folder mutations** (not reusing `activity_events`).
   - Grounded finding: there's already a working precedent for a high-volume, one-row-per-mutation event table in this exact code path — `sync_events`, written by the very same `recordEvent` call already in `PostgresStore`. That table already captures `event_type`, `entity_type`, `entity_id`, `user_id`, `workspace_id`, `payload`, `created_at` — nearly everything "audit" would want, on every existing bookmark/folder mutation, right now, with no new code. What it lacks relative to "audit" semantics: it's not clearly organization-scoped end-to-end for admin-facing reads (worth double-checking retention/read-access assumptions), and it has no admin-facing list endpoint or UI (the extension's `replayEvents` reads it for sync catch-up, not for a human audit view).
   - Pros: Avoids polluting the low-volume `activity_events`/`ActivityPage` entirely; `sync_events` already proves the write pattern works at whatever volume sync already produces.
   - Cons: A second, code-and-product surface to build and reason about; `sync_events`' current retention/pruning policy relative to a compliance-grade "audit trail" was not investigated in this session.
   - Effort: Medium-High.

## Recommendation

Not resolved here — exploration only. The strongest grounded fact to weigh: options 2 and 3, as originally hypothesized, don't map onto anything that exists in the code today (no live console-vs-sync distinction, no batch transaction to summarize), so choosing between them isn't a "pick the cleanest one" decision — it's "build new infrastructure first." Option 1 is the only one that's a pure wiring task matching the existing `organizations`/`workspaces`/`groups` pattern exactly, but it inherits a real, demonstrated gap: `ActivityPage.tsx` has no `kind` filter today at any layer (SQL, HTTP, UI), so mixing in a materially higher-frequency event class without also addressing that gap would degrade the feed's usefulness for its original admin-console purpose.

## Risks

- `bookmarks.RegisterRoutes` being dead code means any assumption of a "manual bookmark edit is different from sync" distinction is currently false — a proposal built on that premise would not match production behavior.
- Chrome's native bulk-import path (`chrome.bookmarks.onCreated` firing in bursts) is the actual volume risk, not a batch endpoint — no in-repo test or fixture models this, so there's no concrete "typical/max" number to size a solution against from evidence alone.
- `activity/service.go`'s doc comment ("zero callers in this work unit") is stale/misleading relative to the actual codebase state — worth correcting regardless of what's decided here.
- `ActivityPage.tsx`/`ListByOrganization` have no `kind` filter; adding any high-frequency `Kind` values without also adding filtering is a product-usability risk for the existing org-admin audience the page was built for.
- `sync_events`' retention/read-access model wasn't investigated in this session — before recommending option 4, its current growth/pruning behavior should be confirmed, not assumed.

## Ready for Proposal

Yes, with a flag: the user's framing rested on premises (a live console-vs-sync split, a batch-transaction boundary) that this exploration found do not exist in the code. Surface this correction before `sdd-propose` picks a direction, since it removes two of the four volume-handling options as "pick this cleanly" choices and reframes them as "build new infrastructure first."
