## Exploration: invitation-email-delivery

### Current State

**Backend — invitation creation never sends mail.** `backend/internal/mailer` (package `mailer`, `NewSMTP(cfg config.MailConfig) Mailer`, `Mailer.Send(ctx, Message) error`, `ErrDisabled`) is fully implemented and tested (`backend/internal/mailer/mailer.go`, `smtp.go`, unit + opt-in Mailpit smoke tests), but `backend/cmd/api/main.go` never imports `internal/mailer` or constructs a mailer — confirmed by reading the full file (`main.go:1-141`); this matches `openspec/changes/smtp-infrastructure/design.md` line 12, which explicitly deferred "a future composition root constructs `mailer.NewSMTP(cfg.Mail)` and injects it into that workflow."

`config.MailConfig` (`backend/internal/config/config.go:58-108`) has `Enabled, Host, Port, Timeout, TLSMode, AuthMode, Username, Password, FromAddress, FromDisplayName, ReplyTo` — no field for a public base URL to build an accept-invitation link (e.g. `https://admin.urlises.lab.dtfuria.xyz/invitations/{token}`). The closest existing value is `CORS_ALLOWED_ORIGINS` (`config.go:196-198`, defaulting to `http://localhost:5173,http://127.0.0.1:5173`; production compose sets it to `https://admin.urlises.lab.dtfuria.xyz` — `docker-compose.prod.yml:33`), but that's a comma-separated allow-list, not a canonical single origin, so it is not safely reusable for link construction — a new config field is needed.

`Service.CreateInvitationTx` (`backend/internal/organizations/service.go:356-440`) creates the token/DB row inside a caller-supplied `pgx.Tx` and returns an `Invitation` containing `Email`, `Role`, `Token`, `InvitedByUserID` (a raw user ID, not email/name), `OrganizationID` — but it never queries the organization name or the inviter's email/display name. (`AcceptInvitation`'s `loadInvitationForUpdate`, `service.go:694-724`, is the only place that joins `organizations` for the name — that code path runs later, at accept time, not at creation time.) So building an invitation email with org name and inviter identity requires additional queries inside/around `CreateInvitationTx`.

`invitations.expires_at` (`backend/migrations/000002_admin_backend_foundation.sql:25`) is a nullable `TIMESTAMPTZ` with no default, and the `INSERT` in `CreateInvitationTx` (`service.go:413-418`) never sets it — so today every invitation's `ExpiresAt` is permanently `NULL` (never expires; `AcceptInvitation`'s expiry check at `service.go:514` treats `NULL` as "never expires"). An invitation email that states a concrete expiry date cannot do so honestly without also setting `expires_at`, which is data-lifecycle behavior, adjacent scope worth flagging even though not explicitly requested.

**Route wiring and the transaction boundary.** In production, `main.go:105` always passes `idempotencyExecutor` to `organizations.RegisterRoutes`, so the real `POST /organizations/{organizationId}/invitations` handler (`handler.go:139-183`) always takes the idempotent branch, calling `executor.Execute(...)` (`handler.go:163-168`) — the simple form of `httpapi.IdempotencyExecutor` (`idempotency.go:118-129`), whose inner `command` signature is `func(ctx, tx) (SafeResult, error)`. Critically, `IdempotencyExecutor` also exposes a richer primitive, `ExecutePrepared` (`idempotency.go:133-174`), whose `Command` type is `func(context.Context, pgx.Tx) (SafeResult, PostCommit, error)` where `PostCommit = func(context.Context) error` — and `ExecutePrepared` calls that `PostCommit` hook only after `tx.Commit(ctx)` succeeds (`idempotency.go:170-173`). The simple `Execute` wrapper (used today) discards the hook by always passing `nil` (`idempotency.go:123-126`). This `PostCommit` mechanism is the natural, already-existing seam for "send the email only once the invitation row is durably committed, without blocking or being part of the DB transaction" — but using it for invitations means switching that route from `Execute` to `ExecutePrepared` (or wrapping the `command` to return a real hook), which is a small but real interface change to `routeService`/`creationTxService` in `handler.go:14-28`.

The non-idempotent path, `Service.CreateInvitation` (`service.go:340-354`, its own `tx.Begin`/`tx.Commit`), is only reachable in production if `RegisterRoutes` were called with no executor — which `main.go` never does. It's exercised today only via the `routeService` interface's direct `CreateInvitation` method in unit-test stubs (`organizations/handler_test.go:15-60`), not via the real HTTP route.

`mailer.SMTPMailer.Send` (`smtp.go:35-111`) dials synchronously per call with a bounded deadline (`config.Mail.Timeout`, default 10s per `config.go:154`), no connection pooling/reuse, and returns `ErrDisabled` immediately if `MAIL_ENABLED=false` (`smtp.go:36-38`) — which is the default (`config.go:146`). `mailer.Message` composition (`smtp.go:124-169`) requires both `Text` and `HTML` non-empty or it errors (`smtp.go:125`), so any invitation email — even a plain, unbranded one — must still supply a minimal HTML alternative, not skip it.

**Frontend — no accept-invitation route exists at all.** `admin-web/src/app/router.tsx` (`router.tsx:62-114`) defines only `/login`, `/register`, an authenticated `/` subtree (with `setup/organization`, `organizations/new`, `members`, `groups`, `workspaces`, `access`), and a catch-all `*` that `Navigate`s to `/`. There is no `/invitations/:token` route, no API function, and no type for `POST /invitations/{token}/accept` anywhere in `admin-web/src` (confirmed via repo-wide grep for "accept"/"invitations/{token}"/"invitationToken" — zero matches). If a visitor followed a hypothetical invite link today, the unmatched path would hit the catch-all → `/` → `RequireSession` (`router.tsx:20-35`) → since they're anonymous, `Navigate` to `/login`, silently dropping the token with no mechanism to recover it.

`RequireSession` (`router.tsx:20-35`) is the existing session gate: `status === "anonymous"` → `/login`; `status === "setupRequired"` → `/register`; otherwise renders `<Outlet/>`. `OrganizationSetupPage` (`admin-web/src/app/views/OrganizationSetupPage.tsx`) is nested under this gate at `setup/organization` and is architecturally the closest analog for a new authenticated "accept invitation" landing page (same shell pattern: `AppShell compact`, `ui-login-card`, `FormRow`, `DataState` for errors, `useAuth`/`useOrganization`).

Neither `LoginPage` (`admin-web/src/app/views/LoginPage.tsx`) nor `RegisterPage` (`admin-web/src/app/views/RegisterPage.tsx`) read or forward any redirect/return-url query parameter today — confirmed no `useSearchParams`/`useLocation` usage in either file. After `signIn`/`signUp` succeeds, `AuthProvider` (`AuthProvider.tsx:104-127`) just flips `status` to `"authenticated"`; navigation back to `"/"` happens implicitly via the route guards, not an explicit redirect target. There is no existing "return to X after login" concept anywhere in the codebase — this is new plumbing, not a reuse of an existing pattern.

A structural constraint on the frontend design: `AcceptInvitation` on the backend (`service.go:517-519`) requires `strings.ToLower(record.Email) == userEmail` (the authenticated user's own email) or it returns `ErrInvitationEmailMismatch` (400). `RegisterPage` (`RegisterPage.tsx:11`) lets the user type any email freely with no prefill. So if an invitee without an account follows the link straight to `/register` and types a different email than the one invited, registration itself succeeds but the subsequent accept call will 400 — a silent-until-the-last-step UX trap unless the accept flow pre-fills/locks the email field when arriving via a token.

`admin-web/src/lib/api/organizations.ts`'s `normalizeInvitation` (`organizations.ts:17-30`) reads `invitation.invitedByEmail` from the raw API response, but the backend's list-invitations JSON shaping (`handler.go:219-221`, and the `ListInvitations` query at `service.go:451-459`) never returns an `invitedByEmail` field — it's always `undefined` today. This is a pre-existing, independent gap in the admin-web member-invite UI (not part of this change's scope), flagged only because if the design phase decides to add inviter identity data to the backend for the email body, extending the same response to include `invitedByEmail` would fix this for free.

### Affected Areas
- `backend/internal/mailer/mailer.go`, `smtp.go` — read-only; the port/adapter are stable and out of scope to modify. Any invitation code depends on `Mailer.Send`/`Message` as-is.
- `backend/internal/config/config.go` — needs a new field (e.g. `PublicBaseURL`) plus validation, to build the accept-invitation link. `MailConfig` itself needs no changes.
- `backend/internal/organizations/service.go` — `CreateInvitationTx` (`:356`) needs org name + inviter identity available to build the email content; `Invitation`/`invitationRecord` structs may need extension.
- `backend/internal/organizations/handler.go` — `routeService`/`creationTxService` interfaces (`:14-28`) and the `POST /organizations/{organizationId}/invitations` handler (`:139-183`) need to either invoke the mailer directly or switch to `httpapi.IdempotencyExecutor.ExecutePrepared` to use its `PostCommit` hook.
- `backend/internal/httpapi/idempotency.go` — no code change expected, but its `ExecutePrepared`/`PostCommit` primitive (`:37-39`, `:133-174`) is the key existing seam to reuse rather than reinvent.
- `backend/cmd/api/main.go` — needs to construct `mailer.NewSMTP(cfg.Mail)` (or a disabled/no-op variant) and inject it into the invitation route, mirroring the `invitationAccepterAdapter` pattern already used for accept (`main.go:26-32`).
- `admin-web/src/app/router.tsx` — needs a new route for accepting an invitation (design phase decides `/invitations/:token` public entry point vs. query-param-through-auth).
- `admin-web/src/app/providers/AuthProvider.tsx`, `OrganizationProvider.tsx` — likely no structural change, but any new accept page will consume `useAuth`/`useOrganization` the same way `OrganizationSetupPage` does.
- `admin-web/src/app/views/RegisterPage.tsx`, `LoginPage.tsx` — need new plumbing to accept/forward a return target and, for `RegisterPage`, likely a prefilled/locked email when arriving via an invite token.
- `admin-web/src/lib/api/organizations.ts` or a new `admin-web/src/lib/api/invitations.ts` — needs a new function for `POST /invitations/{token}/accept` (none exists today).
- `backend/migrations/` — only if the design phase decides to also set `expires_at` at creation time (adjacent, not core, scope).

### Approaches

**A. Backend trigger point / delivery mode**

1. **Best-effort send via `PostCommit` hook on `ExecutePrepared`** — switch the invitation-creation route from `executor.Execute` to `executor.ExecutePrepared`, returning a `PostCommit` closure that calls `mailer.Send` after the DB transaction is durably committed; log-and-swallow delivery failures (never roll back or fail the HTTP response for a mail error).
   - Pros: reuses an existing, already-tested primitive exactly built for this ("run after commit, never before"); keeps invitation creation available even if SMTP/Mailpit is down or slow, matching `smtp-infrastructure`'s own stated risk ("do not establish an SMTP connection at API startup... surface delivery errors only when a future caller invokes Send"); avoids adding SMTP latency (up to `MAIL_TIMEOUT`, default 10s) to the synchronous HTTP response; keeps the change bounded to `organizations` + `main.go` wiring, no new infra.
   - Cons: requires changing the `routeService`/`creationTxService` interface shape and the handler's idempotency call from `Execute` to `ExecutePrepared`, a slightly bigger diff than a naive inline call; a failed send is silent to the admin unless explicitly logged (no outbox/retry, which is intentionally out of scope).
   - Effort: Medium.

2. **Synchronous inline `mailer.Send` call inside `CreateInvitationTx`/`CreateInvitation`, before commit or right after** — call the mailer directly in the service method and propagate/log its error.
   - Pros: smallest possible code diff; no interface changes to `routeService`.
   - Cons: if called before commit, an SMTP failure would need to either fail the whole invitation (poor UX — admin blocked from inviting because mail relay hiccupped) or be swallowed with the invitation still committed inside the same function scope (awkward, since the tx is owned by the caller in `CreateInvitationTx`); if called after `tx.Commit()` in `CreateInvitation`'s wrapper, it duplicates logic that already exists as `PostCommit` and doesn't benefit from the idempotency guard (a retried request due to network flakiness could double-send, since idempotency replay only replays the safe HTTP response, not arbitrary side effects triggered outside the receipt); blocks the HTTP response on SMTP dial+send (up to `MAIL_TIMEOUT`).
   - Effort: Low-Medium.

**B. Frontend accept-invitation UX**

1. **Dedicated public `/invitations/:token` route that itself decides where to send the visitor, carrying the token forward via query param through register/login** — add a new top-level route outside `RequireSession`; it reads `useAuth().status`; if anonymous/setupRequired, `Navigate` to `/login?invite={token}` or `/register?invite={token}`; once authenticated, it calls `POST /invitations/{token}/accept` and redirects into the app.
   - Pros: single, obvious entry point matching the "link → page" description in the task; keeps token handling isolated to one component; `LoginPage`/`RegisterPage` only need to learn to read one query param and pass it through, a small, scoped addition rather than a general redirect system.
   - Cons: needs new "return-to" plumbing in both `LoginPage` and `RegisterPage` (currently absent entirely); if `RegisterPage` doesn't prefill/lock the invited email, users can still hit `ErrInvitationEmailMismatch` after registering with a different email — needs explicit design decision (prefill, lock, or clear inline error explaining the mismatch).
   - Effort: Medium.

2. **Reuse `OrganizationSetupPage`'s authenticated-gate pattern — nest `/invitations/:token` under `RequireSession` directly** (like `setup/organization` is today), and let `RequireSession`'s existing redirect to `/login`/`/register` happen, but only after stashing the intended target (e.g. `sessionStorage`) so the app can resume the accept flow post-auth without a URL query param.
   - Pros: no changes needed to the URL query-param contract; leverages the exact same gate every other authenticated page already uses.
   - Cons: session/local storage as the transport for a security-relevant token is less inspectable/debuggable than a URL param, adds a new storage key + read/clear lifecycle, and still needs the same "resume after login" logic just relocated into storage instead of the URL — doesn't actually remove complexity, just moves it, and is less friendly to users who might close/reopen the tab or copy-paste the link into a different browser step.
   - Effort: Medium.

### Recommendation

Backend: **Approach A.1** (`PostCommit` hook via `ExecutePrepared`) is the right fit — it directly reuses infrastructure the codebase already built for exactly this "only after durable commit, never block or fail the primary write" scenario, matches the explicit out-of-scope constraint (no outbox/retry — a logged best-effort attempt is enough), and avoids adding SMTP latency/availability coupling to `POST /organizations/{organizationId}/invitations`. `CreateInvitationTx`'s return value needs to be extended with organization name and inviter email (fetched via one or two additional read queries alongside the existing `requireOrganizationAdmin`/`INSERT`, kept inside the same transaction so the data is transactionally consistent with the invitation row) so the `PostCommit` closure has everything it needs (org name, inviter, invitee email, role, token, and the new `PublicBaseURL` config value) to build the link and message without a second round-trip after commit.

Frontend: **Approach B.1** (dedicated `/invitations/:token` route, token carried via query param through register/login) is more consistent with how URLs/links are expected to behave (shareable, survivable across tabs/devices, inspectable) and keeps the new "return-to" concept narrowly scoped to the invitation flow rather than introducing a general redirect system. The design phase should explicitly decide: (a) whether `RegisterPage` prefills/locks the email from an unauthenticated invitation lookup or just leaves it free-text with a clear mismatch error post-accept, and (b) exact query param naming/placement for `/login` and `/register`.

### Risks
- `invitations.expires_at` is always `NULL` today (no default, never set on insert) — an invitation email cannot state a truthful expiry unless this change also sets one at creation time; needs an explicit scope decision in the proposal (in-scope data fix vs. omit expiry language from the email body).
- `mailer.Message.compose` (`smtp.go:125`) hard-requires non-empty `HTML` in addition to `Text` — every invitation must still produce a minimal HTML alternative or `Send` will error.
- Switching `POST /organizations/{organizationId}/invitations` from `executor.Execute` to `executor.ExecutePrepared` is an interface-shape change to `routeService`/`creationTxService` (`handler.go:14-28`) touching existing test stubs (`organizations/handler_test.go`); must keep the idempotency-replay guarantee intact (a replayed/duplicate request must not re-trigger `PostCommit` — confirmed `ExecutePrepared` only returns a non-nil hook on the fresh-command path at `idempotency.go:170-173`, the replay path returns nil hook at `:161`, so this is already safe by construction, but must not be broken by the wiring).
- `CreateInvitationTx` currently has no org-name/inviter-identity query; adding it inside the same `pgx.Tx` is straightforward but must not weaken the existing `requireOrganizationAdmin` authorization ordering or the pending/member/duplicate checks already in that function (`service.go:371-411`).
- No `PublicBaseURL`-equivalent config exists; must be added to `config.go` with validation (non-empty when `MAIL_ENABLED=true`, well-formed URL) and to `docker-compose.yml`/`docker-compose.prod.yml`/`.env.example`, or invitation links cannot be constructed in any environment.
- `RegisterPage` has no email-prefill mechanism today; without one, users who mistype/change the invited email during registration will hit `ErrInvitationEmailMismatch` (400) only at the final accept step — the design phase must decide how to surface or prevent this.
- `admin-web`'s `normalizeInvitation` already expects an `invitedByEmail` field the backend never sends (`organizations.ts:11,25`) — pre-existing, independent gap; worth a one-line fix if the backend ends up querying inviter email anyway for the mail body, but not required by this change.

### Ready for Proposal
Yes — both gaps are concretely scoped with exact file/line anchors. Two open design decisions should be flagged during proposal/design: (1) whether to set `expires_at` at invitation-creation time so the email can state a real expiry, and (2) the exact query-param contract for carrying the invitation token through `/login`/`/register` and whether `RegisterPage` prefills/locks the invited email. Neither blocks starting the proposal — both can be resolved as proposal-stage decisions.
